## Defekt 1 — C-31 CFAR crasht auf allen 5 Symbolen (BLOCKER H-03) → **FIXED**

**Log-Beweis** (`C31_CFAR_BTCUSDT.err.log`, identisch auf allen 5 Symbolen):

```
File ".../c31_cfar/cyclic_spectrum.py", line 115, in bin_counts
  edges = lo + bin_dt_ms * np.arange(n_bins + 1)
numpy._core._exceptions._ArrayMemoryError: Unable to allocate 1.30 TiB
for an array with shape (178056061487,) and data type int64
```

**Root-Cause:** Die `trades`-Tabelle der Bestands-DuckDB enthält mindestens
eine Zeile mit `ts ≈ 0` (Epoch-ms-Kontrakt verletzt; vermutlich ein
Parsing-Default `timestamp_ms=0`). 178 056 061 487 Bins × 10 ms (feinstes
Familien-Δt) ≙ Spanne 1.78056e12 ms = exakt der Epoch-ms-Wert von
~2026-06-04 ⇒ `lo = min(ts) ≈ 0`, `hi` = Median-Tick von Fenster 0 (Daten
enden 2026-06-11; die 5 Symbole unterscheiden sich nur um ~2 h ⇒ wenige
Ausreißer-Zeilen, keine falsche Einheit der ganzen Spalte). Fenster 0
spannte damit die gesamte Epoche auf → 1.3-TiB-Histogramm.

**Repro:** in der Sandbox exakt reproduziert (synthetische Epoch-ms-Ticks +
eine ts=0-Zeile → identische 1.30-TiB/1.78e11-Bins-Meldung).

**Fix (3 Schichten, alle read-only):**
1. `driver.load_trades_duckdb`: Plausibilitätsfilter
   `ts ∈ [2010-01-01, 2100-01-01] (epoch-ms)` direkt im SQL; gedroppte
   Zeilen werden gezählt und als WARN auf stderr gemeldet. CSV/Parquet-
   Fixtures (relative Timestamps) bleiben ungefiltert.
2. `driver.run`: Spannen-Pre-Check vor jedem Binning → `DataError`
   („corrupt timestamps") statt MemoryError.
3. `cyclic_spectrum.bin_counts`: harter Guard `MAX_BINS = 1e9`
   (legitime 60-Tage-Fenster @10 ms ≈ 5.2e8 bleiben erlaubt) → klare
   `ValueError` statt TiB-Allokation.

**Tests:** `tests/unit/test_c31_cfar.py` neu Abschnitt 9 (3 Regressionstests:
run-DataError, bin_counts-Guard, DuckDB-Loader-Filter inkl. Sekunden-Epoch-
und Zukunfts-Zeile). Suite: **25/25 grün** (22 Bestand + 3 neu).

**Folgefrage (nicht Teil des Fixes):** Die korrupten Zeilen liegen weiterhin
in der Bestands-DB. Kandidat für ein eigenes WP: Herkunft im 1.0-Collector
(`TradeEvent.timestamp_ms`-Parsing) prüfen; Daten selbst sind Schutzgut
(read-only), daher hier nur gefiltert, nicht bereinigt.

## Defekt 2 — C-42-Quick hängt am DuckDB-Open (TIMEOUT 900 s) → **FIXED**

**Log-Beweis** (`short_20260612_082957/C42_QUICK_HAR.err.log`, letzte Zeile):

```
[c42] opening duckdb read-only: E:\Claude\Projects\scinance\data\bybit_edge.duckdb
```
danach 900 s nichts (`steps.tsv`: `C42_QUICK_HAR FAIL 124 900 TIMEOUT nach 900 s`).

**Root-Cause:** DuckDB erlaubt genau einen RW-Prozess; der laufende
1.0-Collector hielt den Lock, der read-only-Open des T2-Laufs (08:29 Uhr)
blockierte. Der Overnight-C42 (16:08, Collector offenbar gerade aus) lief
durch — konsistent mit der Lock-Hypothese.

**Fix (`scripts/c42_repro.py`):**
1. `_open_db_with_timeout`: DB-Open im Daemon-Thread, harter Timeout
   `DB_OPEN_TIMEOUT_S = 30 s`; Timeout UND Lock-Fehler werden auf
   `CLIError` mit klarer Meldung gemappt: „DuckDB gesperrt (laeuft der
   1.0-Collector?) — Workaround: --db-copy“.
2. Neues Flag `--db-copy`: kopiert `.duckdb` (+ `.wal` falls vorhanden)
   nach tempdir, liest die Kopie read-only, löscht sie danach. Verhalten
   ohne Flag unverändert (bis auf Timeout-statt-Hang).
3. Beide Short-Runner (`run_short.sh`/`.ps1`) geben `--db-copy` jetzt als
   Default mit (HAR + LGBM) — der T2-Lauf kann nie mehr am Lock hängen.

**Verifiziert in der Sandbox gegen einen echten gehaltenen RW-Lock:**
ohne Flag → sofortige klare Fehlermeldung mit --db-copy-Hinweis; mit
`--db-copy` → Lesen trotz Lock, Temp-Kopie danach entfernt.
**Tests:** 4 neue in `tests/unit/test_c42_rv.py` (Hang→CLIError,
Lock-Error-Mapping, fremde Fehler unmaskiert, --db-copy-E2E inkl.
Cleanup + Original-unverändert). Suite: **33/33 grün**.

## Defekt 3 — E-15 findet trades_all.csv nicht (BLOCKER H-01) → **FIXED**

**Log-Beweis** (`short_20260612_082957/E15_EVAL.err.log`):

```
E15-EVAL DATENDEFEKT: trades file not found:
E:\Claude\Projects\scinance\edge_research_framework\results\trades_all.csv
```

**Root-Cause:** Die Runner verdrahteten den Trades-Pfad fest auf
`results/trades_all.csv`; der iter-5-Lauf exportierte laut dokumentiertem
`--export-trades`-Aufruf nach `results/trades_iter5/`. `replay_all_results.json`

war falsch.

in `run_short.sh` + `run_short.ps1`:
(1) `results/trades_all.csv` → (2) `results/trades_iter5/trades_all.csv` →
(3) neuester `results/trades_*/trades_all.csv`; erster Treffer gewinnt.
Existiert keiner: **SKIP** mit klarer Meldung (statt FAIL), Hinweis auf
`--export-trades`.

**Verifiziert:** Kaskaden-Logik mit allen 4 Fällen (kein Treffer / nur Glob /
iter5 / direkter Pfad) gegen synthetisches Layout; `bash -n` + kompletter
Dry-Run von `run_short.sh` grün. PS1 spiegelbildlich (kein PowerShell in der
Sandbox — Mechanik identisch zur verifizierten sh-Logik, T2 bestätigt).

## Defekt 4 — Recorder: 3/5 Streams NO_DATA → **option_tickers FIXED · rpi_orderbook/insurance_pool BRAUCHT-RETEST (instrumentiert)**

**Log-Befund** (`RECORDER_LONG.err.log` 8 h, `RECORDER_SMOKE.err.log` 5 min):

1. `[option]` verbindet + subscribed (`tickers.BTC`, `tickers.ETH`), stirbt
   aber **alle ~31 s** clientseitig:
   `connection lost (sent 1011 (internal error) keepalive ping timeout; no
   close frame received)` — exakt `WS_PING_INTERVAL(20)+WS_PING_TIMEOUT(10)`.
   ⇒ Der Options-Endpoint beantwortet RFC-6455-Protokoll-Pings NICHT; Bybit
   verlangt dort den App-Heartbeat `{"op":"ping"}`. Die Linear-Verbindung
   lief dagegen 8 h ohne einen einzigen Reconnect.
2. `messages=5` nach 300 s Smoke = exakt die 5 REST-Polls
   (premium_index_kline). **Null** WS-Messages auf beiden Transporten.
3. Zu `orderbook.rpi.BTCUSDT` / `insurance.USDT` sagen die Logs NICHTS
   Belastbares: `_consume` verwarf Frames ohne `topic` kommentarlos
   („subscription ack / heartbeat") — eine `success=false`-Ablehnung
   (INC-06-Verdacht: kestrel-PRD-Phantom-Topic) wäre unsichtbar geblieben.
   Die Zeile „Subscribed to 3 topic(s)" belegt nur das SENDEN des Requests.

**Fix (eindeutig, log-gestützt) in `recording_engine.py`:**
- `_ws_keepalive_kwargs`: Options-URL → `ping_interval/ping_timeout=None`
  (Library-Keepalive aus); Linear unverändert (1.0-Collector-Verhalten).
- App-Level-Heartbeat `{"op":"ping"}` alle 20 s auf jeder WS-Verbindung
  (`_app_ping_loop`); schlägt der Send fehl, wird die Verbindung geschlossen
  → sauberer Reconnect.
- `_log_control_frame`: Subscribe-Acks werden jetzt geloggt —
  `success=true` als INFO, **`success=false` als ERROR mit komplettem
  Payload** („topic likely does not exist"); Pongs als DEBUG.

**Tests:** 4 neue in `tests/unit/test_recorder_engine.py` (Keepalive-Kwargs,
ERROR-Log bei abgelehnter Subscription, INFO-Ack, App-Ping auf der Leitung,
Subscribe bleibt erste Nachricht). Suite: **22/22 grün**.

**Was der T2-Retest klären muss (KEINE Spekulation als Fix verkauft):**
- `option_tickers`: liefert der Stream mit stabilem App-Ping jetzt Daten?
  (Erwartung: ja — Verbindung starb bisher vor dem ersten Snapshot-Push.)
- `rpi_orderbook` / `insurance.USDT`: Im neuen Log nach
  `SUBSCRIBE/REQUEST REJECTED` suchen. Kommt `success=false` →
  Topic-Name/Endpoint falsch (INC-06: `orderbook.rpi.{symbol}` evtl.
  Phantom bzw. Spot-statt-Linear; `insurance` evtl. nur REST) → dann
  DEC-xx zu Topic-Korrektur oder REST-Poll-Umbau. Kommt `success=true`
  und trotzdem keine Daten → Stream sendet nur eventgetrieben (bei
  insurance plausibel: seltene Updates) → EMPTY_OK-Einstufung prüfen.
  Sandbox hat keinen Bybit-Netzzugang — live nicht verifizierbar.
